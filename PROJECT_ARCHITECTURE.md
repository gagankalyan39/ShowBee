# SHOWBEE — Project Architecture Specification
## High-Concurrency Cinema Seat Booking System

---

## 1. Executive Architectural Overview

**SHOWBEE** is a cinema ticket reservation platform engineered specifically to serve as an empirical testbed for evaluating distributed software architecture patterns and database concurrency controls under heavy contention.

The platform implements two co-existing architectural paradigms:
1. **Modular Monolith (Port 5001)**: A single-process Node.js/Express application encapsulating domain modules (Auth, Movies, Theatres, Shows, Seats, Bookings, Payments, Notifications, System/Admin) with in-process TypeScript function invocations.
2. **Booking Microservice (Port 5002)**: An isolated service boundary that extracts high-contention seat holding, booking checkout, and payment processing into an independent microservice with separate connection pooling, isolated memory space, and network RPC boundaries.

Both architectures operate against a PostgreSQL 15 database instance and are instrumented with Prometheus telemetry (`:9090`) and visualized via Grafana dashboards (`:3001`).

## 2. Key Concepts & Terminology (Beginner-Friendly Guide)

- **Virtual Users (VUs)**: Simulated concurrent client threads generated by load-testing tools (such as Grafana k6) that mimic real human browsers browsing screenings, selecting seats, and completing payment checkouts simultaneously.
- **Throughput (RPS)**: Requests Per Second; the rate at which the application backend successfully ingests, processes, and responds to incoming client requests.
- **Latency (Response Time)**: The elapsed time between a client sending an HTTP request and receiving the full HTTP response:
  - **p50 (Median)**: 50% of all requests completed faster than this time. Represents typical user experience.
  - **p95**: 95% of all requests completed faster than this time. Captures tail latency experienced during contention.
  - **p99**: 99% of requests completed faster than this time. Represents worst-case user experience under load spikes.
- **Lock Attempts**: The number of times concurrent clients attempt to secure exclusive reservation of one or more cinema seats.
- **Lock Conflicts**: The number of times a reservation attempt is rejected (HTTP 409 Conflict) because another concurrent user acquired the target seat first.
- **Pessimistic Locking (PCC)**: A concurrency control strategy where the database transaction explicitly locks rows using `SELECT ... FOR UPDATE` before modifying them. Other transactions attempting to access the same rows must wait until the lock holder commits or rolls back.
- **Optimistic Locking (OCC)**: A concurrency control strategy where transactions do not hold exclusive row locks during inspection. Instead, each row carries a `version` number, and updates succeed only if the version in the database matches the expected version via an atomic Compare-And-Swap (`UPDATE ... WHERE version = $expected_version`).
- **Scalability**: The capacity of a system to handle growing amounts of work by adding hardware or instance resources.
- **Elasticity**: The ability of a system to dynamically adapt its resource capacity in real-time by automatically scaling out during peak surges and scaling in during lulls.
- **Fault Tolerance**: The capability of a software system to continue operating without interruption even when one or more of its underlying components or dependencies fail.
- **Blast Radius**: The maximum scope of damage or user disruption caused when a single service or component fails. In a Monolith, a memory leak or crash impacts all modules; in Microservices, an isolated failure is contained within the microservice boundary.
- **Communication Overhead**: The latency and serialization tax paid when two services communicate over a network (TCP/HTTP serialization) compared to in-process memory function calls.
- **Database Consistency (ACID)**: Guaranteed properties (Atomicity, Consistency, Isolation, Durability) ensuring that database transactions are executed reliably and invariant states (e.g., zero double bookings) are strictly maintained.

## 4. Concurrency Control Mechanisms

### 4.1. Pessimistic Concurrency Control (SELECT FOR UPDATE)
Pessimistic locking is implemented in `backend/src/routes/seats.ts` and `booking-service/src/routes/seats.ts`:
```sql
SELECT ss.id, ss.status, ss.locked_by, ss.lock_expires_at, ss.version
FROM show_seats ss
WHERE ss.id = ANY($1::uuid[]) AND ss.show_id = $2
ORDER BY ss.id ASC
FOR UPDATE;
```

**Key Engineering Guarantees:**
1. **Deterministic Lock Ordering**: Row IDs are explicitly deduplicated and sorted via `ORDER BY ss.id ASC`. This mathematically prevents PostgreSQL deadlocks (`SQLSTATE 40P01`), ensuring transactions always acquire locks in identical serial order.
2. **Safe Hold Re-acquisition**: If a seat status is `HELD` but `lock_expires_at < NOW()`, the pessimistic lock permits the new transaction to reclaim the seat.
3. **Bounded Transaction Scope**: The transaction immediately commits upon updating status to `HELD` with `version = version + 1`, releasing the database row lock in less than 8ms.

### 4.2. Optimistic Concurrency Control (Atomic Compare-And-Swap)
Optimistic locking avoids holding database row locks during validation:
```sql
-- Step 1: Read current state without locks
SELECT id, status, version FROM show_seats WHERE id = ANY($1::uuid[]) ORDER BY id ASC;

-- Step 2: Atomic Compare-And-Swap (CAS) Update
UPDATE show_seats
SET status = 'HELD',
    locked_by = $1,
    lock_expires_at = NOW() + INTERVAL '5 minutes',
    version = version + 1,
    updated_at = NOW()
WHERE id = $2 
  AND version = $3 
  AND (status = 'AVAILABLE' OR (status = 'HELD' AND lock_expires_at <= NOW()));
```

**Key Engineering Guarantees:**
1. **Affected Row Count Verification**: If another transaction updated the seat in the interim, its version was incremented. The `WHERE version = $3` predicate causes `rowCount === 0`.
2. **Immediate Rollback on Conflict**: If `rowCount === 0`, the transaction rolls back, releases any acquired changes, records `showbee_seat_lock_conflicts_total{mode="optimistic"}`, and returns HTTP 409 Conflict.
3. **No Lock Overhead during Reads**: Non-conflicting reads operate without database row lock contention.

## 5. Database Schema & ACID Invariants

### 5.1. Database-Level Anti-Double-Booking Trigger
Even in the theoretical event of an application software fault or race condition, PostgreSQL physically aborts any transaction attempting to double-book a seat:
```sql
CREATE OR REPLACE FUNCTION trg_check_duplicate_seat_booking()
RETURNS TRIGGER AS $$
DECLARE
  v_booking_status booking_status;
BEGIN
  SELECT status INTO v_booking_status FROM bookings WHERE id = NEW.booking_id;
  IF v_booking_status IN ('CONFIRMED', 'PENDING') THEN
    IF EXISTS (
      SELECT 1 FROM booking_seats bs
      JOIN bookings b ON bs.booking_id = b.id
      WHERE bs.show_seat_id = NEW.show_seat_id
        AND bs.id <> COALESCE(NEW.id, '00000000-0000-0000-0000-000000000000'::uuid)
        AND b.id <> NEW.booking_id
        AND b.status = 'CONFIRMED'
    ) THEN
      RAISE EXCEPTION 'ACID VIOLATION: Seat % is already CONFIRMED in another booking', NEW.show_seat_id;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

### 5.2. Idempotency Key Deduplication
To protect against repeated network submissions or duplicate user clicks:
```sql
CREATE UNIQUE INDEX idx_bookings_user_idempotency 
  ON bookings(user_id, idempotency_key) 
  WHERE idempotency_key IS NOT NULL;
```

## 6. End-to-End Booking Lifecycle

```
[Available Seat] 
       |
       | User submits hold request (/api/shows/:id/seats/hold)
       v
   [HELD (5 Min Expiry)] 
       |
       +---> [Hold Expires (>5 mins)] ---> [Reverted to AVAILABLE]
       |
       | User submits booking order (/api/bookings)
       v
   [PENDING Booking Order Created]
       |
       +---> Payment Fails / Cancelled ---> [Reverted to AVAILABLE]
       |
       | User submits payment confirmation (/api/payments)
       v
   [CONFIRMED Booking & BOOKED Seat] (QR Code Generated, Zero Double-Booking Invariant)
```
